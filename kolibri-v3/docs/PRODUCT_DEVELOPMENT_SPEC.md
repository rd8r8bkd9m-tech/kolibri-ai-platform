# Kolibri V3 — техническое задание на разработку продукта

- Статус: основной продуктовый контракт разработки
- Версия: 1.0
- Дата: 1 августа 2026 года
- Канонический код: `kolibri-v3/`
- Production: `https://kolibriai.ru/app`

## 1. Назначение продукта

Kolibri V3 — универсальная агентная рабочая среда, в которой пользователь
формулирует задачу естественным языком, агент выполняет работу, создаёт и
обновляет структурированные артефакты, а пользователь контролирует результат
в одном интерфейсе.

Первый коммерческий vertical pack — строительство и сметы. Архитектура ядра
не должна зависеть от строительства: тот же продукт впоследствии подключает
медицинские, сервисные, производственные и другие вертикали через
версионированные capability/renderer contracts.

## 2. Продуктовый результат

Пользователь должен иметь возможность:

1. Войти с desktop, Safari/Chrome mobile или установленного приложения.
2. Создать проект обычным сообщением в чате.
3. Получать потоковый ответ любого разрешённого агента в едином UI.
4. Создать из свободного описания структурированную смету.
5. Изменять существующую смету сообщениями и в редакторе без создания
   несвязанной новой версии.
6. На основе утверждённой версии сметы создавать КП, договор, счёт и акты.
7. Возобновить работу после перезагрузки или на другом устройстве.
8. Видеть источники, версии, расчёты, историю действий и статус выполнения.
9. Владелец платформы — управлять клиентами, агентами, runtime и релизами из
   отдельного control plane.

## 3. Роли

| Роль | Полномочия |
| --- | --- |
| Пользователь | чаты, проекты, документы, разрешённые vertical packs |
| Участник проекта | доступ к назначенным проектам и действиям по роли |
| Владелец организации | пользователи и данные своей организации |
| Platform owner | глобальный control plane, клиенты, runtime, агенты, релизы |
| Trusted developer agent | работа только в явно делегированном workspace и профиле |
| Service/worker identity | ограниченная машинная роль с lease и audit trail |

Права всегда вычисляет backend. Наличие элемента UI или клиентского флага не
является авторизацией.

## 4. Информационная архитектура

Основные разделы продукта:

- **Чат** — центральная точка постановки задач и получения результата;
- **Проекты** — объекты, участники, связанные чаты и документы;
- **Документы** — сметы, КП, договоры, счета, акты и файлы;
- **Справочники** — единый список нормативов, ресурсов, цен и шаблонов;
- **Настройки** — профиль, внешний вид, модели, уведомления и устройства;
- **Управление платформой** — отдельная owner-only поверхность.

Название раздела и его навигационный элемент отображаются один раз. Страница
не повторяет «Проекты / Документы / Справочники» в нескольких
вложенных заголовках, хлебных крошках и карточках без смысловой причины.

## 5. Desktop shell

### 5.1. Трёхзонная композиция

```text
┌──────────────┬───────────────────────────────┬────────────────────┐
│ Левый sidebar│ Основная рабочая область      │ Context panel      │
│ навигация    │ чат                           │ выбранный контекст │
└──────────────┴───────────────────────────────┴────────────────────┘
```

### 5.2. Левый сайдбар

Текущая desktop-концепция сохраняется. Сайдбар отвечает только за глобальную
навигацию:

- новая беседа;
- недавние беседы;
- Проекты, Документы, Справочники;
- профиль и настройки;
- owner-only вход в управление платформой.

Сайдбар не показывает содержимое правой контекстной панели и не меняется при
мобильной разработке. Переключение бесед должно быть мгновенным, без вспышки
«Новая беседа», сброса выбранной беседы или самопроизвольного закрытия desktop
sidebar.

### 5.3. Правая контекстная панель в модели Codex

Текущая правая панель с дублирующим «Рабочим столом» заменяется единой
контекстной панелью. Она не является вторым маршрутом или второй навигацией.

Обязательное поведение:

- открывается одной кнопкой в header и закрывается той же кнопкой или `Esc`;
- ширина 320–720 px, resize в допустимых границах, состояние сохраняется;
- основной контент не перезагружается и не теряет scroll/focus;
- panel title отражает контекст, а не всегда «Рабочий стол»;
- при отсутствии выбранного объекта показывает компактный empty state;
- никогда не создаёт дубликат страницы «Рабочий стол»;
- на ширине ниже desktop breakpoint превращается в modal/bottom sheet.

Idle-состояние повторяет предоставленный владельцем Codex-референс:

- чистая белая/тёмная поверхность с одной левой вертикальной границей;
- launcher-строки без карточек: **Проверка**, **Терминал**,
  **Браузер**, **Файлы**, **Проекты**;
- слева единообразная 18–20 px иконка, справа — необязательный shortcut badge;
- блок launcher-строк расположен около визуального центра панели;
- верхняя панель содержит только действия fullscreen/minimize/panel toggle;
- нажатие launcher заменяет idle-содержимое инструментом в той же зоне;
- закрытие инструмента возвращает launcher-список, не открывает «Рабочий стол».

Рабочая модель:

- чат является постоянным центральным canvas;
- на desktop чат остаётся смонтированным и видимым при любом состоянии правой
  панели; правая панель никогда не заменяет и не перекрывает его;
- «Проверка» показывает факты, результаты тестов и проверки текущей задачи;
- «Терминал» показывает связанную агентную terminal-сессию;
- «Браузер» показывает браузер текущей задачи и его console/network status;
- «Файлы» показывает реальные артефакты проекта, включая сметы и документы;
- «Проекты» показывает проекты и связанные с выбранным проектом документы;
- выбор файла открывает компактный редактор в той же правой панели; кнопка
  «Назад» возвращает к списку документов;
- интерактивная смета одновременно остаётся доступной в сообщении чата и в
  правой панели, но обе поверхности читают и сохраняют один и тот же
  `projectId` / `documentId` / `version`;
- один и тот же артефакт не рендерится одновременно двумя независимыми
  редакторами; обе поверхности используют одну versioned state-модель.

Контент правой панели зависит от выбранного контекста, при этом центральная
область остаётся чатом:

| Основная область | Правая панель |
| --- | --- |
| Чат | ход задачи, инструменты, артефакты, файлы и свойства беседы |
| Смета в чате | тот же сохранённый документ, версия, источники и редактор |
| Проект | объект, участники, статус, связанные документы |
| Документы | список файлов, preview/редактор, согласование и экспорт |
| Справочник | фильтры, происхождение, регион, дата актуальности |
| Dev mode | план, tool calls, diff, terminal output, tests, artifacts |

Отдельный плавающий или закрепляемый chat widget не используется: он дублирует
центральный чат, создаёт два состояния одной беседы и относится к удалённой
Canvas-концепции.

В режиме агента события идут в хронологическом порядке. Tool call по умолчанию
свёрнут в одну строку: иконка, действие, статус и длительность. Раскрытие
показывает вход/выход в безопасном объёме; 150 инструментов не выталкивают
текущий ответ из видимой области. Активный шаг автоматически остаётся видимым,
но ручная прокрутка пользователя не перехватывается.

### 5.4. Header

Header содержит только глобально необходимые действия: название текущего
контекста, статус runtime при необходимости, переключатель правой панели и
контекстные primary actions. Иконки имеют единый размер и берутся из одного
icon registry. Дубли навигационных заголовков удаляются.

Dropdown проекта в header меняет контекст беседы, но не подменяет центральный
canvas. Сметы и документы открываются из правой панели. Старый внутренний Canvas
header, повторные вкладки, title bars и launcher «Рабочий стол» не рендерятся.
Смена проекта или документа не сбрасывает беседу, draft и позицию прокрутки.

## 6. Mobile web, PWA и native

### 6.1. Один пользовательский origin

`3103` локально и `kolibriai.ru/app` в production — единственные
пользовательские точки входа. Gateway выбирает desktop Next или mobile
Expo/React Native Web, но оба клиента используют один backend, auth и данные.

### 6.2. Mobile shell

- отдельная mobile-композиция, а не сжатый desktop;
- ChatGPT-like header, hamburger, история бесед и компактный composer;
- safe area, экранная клавиатура, touch targets и системная тема;
- светлая, тёмная и системная темы;
- long press беседы: закрепить, переименовать, архивировать, удалить;
- правая desktop-панель отображается как контекстный full-screen sheet;
- личный кабинет, проекты, документы, справочники и редактор смет
  полнофункциональны;
- PWA работает в Safari/Chrome без обязательной установки native app.

Expo/React Native является основой iOS/Android клиента. Tauri применяется как
edge/desktop/kiosk shell там, где нужен Rust host и системные интеграции; он не
заменяет browser/PWA и не владеет продуктовой логикой.

## 7. Chat и агентный runtime

### 7.1. Единый adapter

Codex, MiMo Code и будущие модели подключаются через один provider-neutral
adapter. UI сообщений, reasoning summary, tool calls, streaming, cancel,
retry и ошибки одинаковы для всех providers. Provider-specific код находится
только в execution adapter, а не в React-компонентах.

### 7.2. Режимы

- **Standard** — вопрос, документы, поиск, генерация артефактов;
- **Developer** — trusted-agent задачи в назначенном workspace;
- режим разрешается backend по роли, tenant policy, runtime capability и
  workspace binding;
- production developer mode выполняется на Agent Host/Home, а не shell внутри
  публичного API process.

### 7.3. Поток событий

Минимальный контракт: run started, ordered text deltas, tool started/progress/
finished, artifact created/updated, run finished/error/cancelled. События имеют
server cursor, idempotency binding и восстанавливаются после reconnect.

### 7.4. Надёжность

- persistent runtime не поднимается заново для каждого запроса;
- первое содержательное событие должно появляться без ожидания полной работы;
- отмена останавливает server run;
- нет silent fallback на другого агента;
- нет fake/echo ответов при недоступном runtime;
- ошибка типизирована и допускает безопасный retry.

## 8. Проекты и артефакты

Первое принятое сообщение атомарно создаёт проект, объект, основной thread и
versioned document slots. Chat является интерфейсом управления этими сущностями,
но не источником истины.

Артефакты:

- исходные данные;
- смета;
- коммерческое предложение;
- договор;
- счёт;
- акт/КС-2/КС-3;
- файл, изображение, отчёт и другие renderer-defined types.

Каждый артефакт имеет ID, проект, тип, версию, статус, автора, timestamps,
provenance и связь с run/message. Повторное редактирование создаёт следующую
версию того же артефакта.

## 9. Строительный vertical pack

### 9.1. Генерация сметы

Пользователь передаёт произвольное описание. Система:

1. извлекает исходные параметры и явно показывает условия расчёта;
2. нормализует регион, площадь, конструктив, состав работ и уровень цен;
3. строит структурированный estimate draft;
4. рассчитывает объёмы и итоги server-authoritative движком;
5. показывает источники, дату цен, НДС и confidence;
6. сохраняет версию и открывает интерактивный редактор.

Детализация не подгоняется под фиксированное число строк. Каждая отличающаяся
операция, материал, оборудование или услуга формируется отдельной позицией.
Для крупных объектов смета строится секционными пакетами и может содержать
тысячи строк без продуктового ограничения. Накладные расходы, налоги и резерв
не скрываются в ценах: без заданных правил они остаются явными условиями,
требующими уточнения.

Одинаковые нормализованные входные данные, версия справочников и версия
расчётного движка дают одинаковый результат. Модель не вычисляет итоговые
суммы самостоятельно.

### 9.2. Редактирование

Фразы «добавь мягкую кровлю», «измени площадь» или «замени материал» должны
создавать изменение текущей выбранной сметы, пересчитывать зависимые строки и
сохранять новую версию. UI после открытия показывает именно сохранённый итог
выбранной версии.

### 9.3. Rust kernel

Расчётный модуль размещается в `packages/estimate-kernel-rs`, не содержит UI,
SQL или provider code и работает по versioned JSON contract. Переключение на
Rust разрешено только после golden-corpus паритета с authority calculation.

## 10. Документы

КП, договор, счёт и акты строятся из выбранной сохранённой версии сметы.
Документ хранит ссылку на source estimate version и не меняется скрытно после
редактирования сметы. Поддерживаются preview, версии, статус согласования и
экспорт PDF/XLSX/DOCX. Подписание, платёж и публикация являются отдельными
явно авторизованными действиями.

## 11. Справочники

Одна страница «Справочники» содержит единый список и верхние фильтры. Убираются
повторные заголовки и вложенные карточки с тем же названием. Запись справочника
содержит единицу, регион, дату, источник, налоговый статус и уровень доверия.

## 12. Owner control plane и Dev IDE

Owner-only поверхность включает:

- организации, пользователей, планы, лимиты и сессии;
- разрешение dev mode и доступные runtime profiles;
- execution nodes, health, очереди, leases и версии adapters;
- задачи агентов, live progress, tool calls, diff, tests и artifacts;
- deploy, restart и rollback как durable operations;
- аудит административных действий и общий kill switch;
- storage dashboard с безопасной оценкой очищаемых данных.

Dev IDE использует ту же модель отображения, что Codex: чат остаётся в центре,
а план, инструменты, файлы, diff, terminal и тесты находятся в правой
контекстной панели. Browser никогда не получает provider credentials или
неограниченный shell напрямую.

## 13. Архитектура и владельцы

```text
Web/PWA Next ─┐
Expo mobile ──┼─> same-origin BFF/API ─> V3 Product/Data backend
Tauri shell ──┘                            │
                                          ├─> Rust kernels
                                          └─> Home/A2A/Agent Host
```

- backend + migrations — authority пользователей, проектов, чатов,
  артефактов и версий;
- Rust kernel — детерминированные side-effect-free вычисления;
- Provider Execution Authority — credentials и выполнение providers;
- web/mobile — представление и локальный ephemeral UI state;
- `deploy/portable` — единственный release lane.

Нельзя использовать parent legacy как upstream, fallback или deployment input.

## 14. Компонентная модель UI

- `components/ui` — Button, IconButton, Input, Dialog, Drawer, Tabs, Tooltip;
- shared composition — PageHeader, ContextPanel, ListRow, EmptyState,
  StatusBadge, ResizablePanel;
- feature components — chat, workspace, estimates, documents, admin;
- один icon registry, одна система размеров, spacing, typography и themes;
- компонент реализуется один раз и переиспользуется;
- page/shell компоненты только композируют features и state;
- provider-specific UI-компоненты запрещены.

Целевой размер файла не является самоцелью, но компонент с несколькими
независимыми обязанностями декомпозируется по состоянию, представлению и
feature boundary. Механическое перемещение одинакового количества кода между
файлами не считается рефакторингом.

## 15. API, данные и миграции

- HTTP schemas authority-first на backend;
- mutations имеют idempotency key, auth, origin/CSRF policy и audit там, где
  требуется;
- миграции append-only и применяются до открытия backend port;
- browser не создаёт fallback-данные;
- общий contract generation используется web/mobile/backend;
- ошибки имеют стабильный `code`, безопасный `message` и correlation id.

## 16. Нефункциональные требования

### Производительность

- UI отвечает на ввод и навигацию без блокировки main thread;
- длинные списки виртуализируются и реально прокручиваются;
- chat сохраняет scroll anchor при streaming;
- desktop и mobile bundles разделены внутренне gateway, но доступны через
  один origin;
- above-the-fold media загружается с корректным приоритетом.

### Доступность

- keyboard navigation, focus-visible, `Esc`, semantic labels;
- touch target не менее 44×44 pt на mobile;
- системные font scaling, contrast и reduced motion;
- screen reader labels для icon-only controls.

### Надёжность и безопасность

- session revocation, CSRF, tenant isolation, audit log;
- secrets только в execution authority;
- backup/restore и rollback rehearsal перед production;
- release из чистого commit через `deploy/portable`;
- runtime health содержит service и instance identity.

## 17. QA и приёмка

Каждая функция проходит:

1. contract/unit tests;
2. typecheck и architecture boundaries;
3. browser QA desktop и mobile через пользовательский origin;
4. console/network inspection без необработанных ошибок;
5. loading, empty, success, error, retry и permission states;
6. регрессию чата, навигации, auth и сохранения данных;
7. production-like build и smoke against release artifact.

Для полной сметы обязательны два независимых QA-уровня:

- product pipeline test отправляет настоящий публичный AG-UI запрос и
  проверяет 1000+ строк, сохранённую ревизию, каталог документов и экспорт;
  детерминированной может быть только внешняя граница модели, а не продуктовый
  маршрут или предметная область;
- live-model acceptance запускается командой
  `npm run test:qa:estimate:live` с отдельной авторизованной QA-сессией. Он
  требует доступную GPT или MiMo, не принимает fixture/server provider,
  проверяет минимум 1000 строк и не может считаться пройденным при отсутствии
  живого model runtime.

Штукатурный Estimate Engine разрешён только как явно выбранный специальный
расчёт. Общий запрос «составь смету» не может неявно подменяться штукатурным,
домовым или другим заранее подготовленным шаблоном.

Отдельная оперативная матрица находится в `docs/QA_RELEASE_TZ.md`.

## 18. Этапы реализации

### P0 — стабильная основа

- единый `3103`, один backend и корректный lifecycle;
- рабочий chat/stream/scroll на desktop и mobile;

## 19. Definition of Done

Функция считается готовой, когда она работает end-to-end на реальных данных,
имеет server-authoritative контракт, не содержит декоративных неработающих
кнопок, покрыта тестом, проверена в браузере, не создаёт console/network error,
сохраняется после reload и не ломает соседний desktop/mobile сценарий.

Правый сайдбар считается готовым, когда он больше не показывает дублирующий
«Рабочий стол», всегда отражает выбранный контекст, сохраняет состояние,
компактно отображает агентные события и проходит desktop/mobile responsive QA.
