# Дизайн-проект Kolibri V3

## Назначение

Kolibri V3 — единое рабочее пространство проектно-строительной фирмы, а не
панель отдельных агентов. Пользователь формулирует задачу одной Kolibri,
наблюдает проверяемый ход работы и получает связанные результаты в
`Chat + Canvas`. Внутренние назначения, A2A-переписка и chain-of-thought не
становятся пользовательским интерфейсом.

## Информационная архитектура

Экран состоит из четырёх устойчивых областей:

1. компактный header с брендом, названием текущего проекта и управлением
   боковыми панелями;
2. левая навигация по проектам и рабочим разделам;
3. центральная поверхность Chat и один canonical `workspace-desktop`;
4. правая контекстная панель с вкладками «Проверка», «Терминал», «Браузер»,
   «Файлы», «Подзадача».

Chat остаётся центральной поверхностью, точкой входа и журналом пользовательских
решений. Явно открытый canonical `workspace-desktop` занимает exclusive
fullscreen и содержит единый мультимодальный Canvas для проекта, документа,
сметы, договора, справочника, браузера, проверки или редактора. Контекстная
панель объясняет и переключает вкладку, но не создаёт второй viewer.

## Геометрия и поведение shell

- Desktop начинается с `1200 px`. Левая панель открыта по умолчанию:
  `272 px`, диапазон `224–360 px`. Правая закрыта по умолчанию:
  `340 px`, диапазон `300–520 px`.
- Между центральной областью и desktop-панелями стоят видимые separator
  controls. Их можно перетаскивать и изменять клавишами стрелок, `Home` и
  `End`; текущий размер сообщается через ARIA.
- Обе панели независимо сворачиваются. Центральная область всегда имеет
  `min-width: 0`, а shell не создаёт горизонтальную прокрутку страницы.
- Ниже `1200 px` панели становятся модальными drawers с backdrop, закрытием по
  `Escape`, focus trap и возвратом фокуса на кнопку открытия. Сохранённая
  desktop-ширина ограничивает, но не ломает ширину drawer. Scrim остаётся
  непрозрачным цветовым слоем без blur.

## Chat + Canvas

Первый экран приветствует пользователя как Kolibri и предлагает четыре
стартовых сценария: рассчитать смету, спланировать проект, подготовить документ
и проверить основания. Выбор сценария заполняет и сразу отправляет обычное
сообщение через официальный assistant-ui primitive; отдельного фиктивного
workflow в браузере нет.

AG-UI provider — единственный transport интерфейса к выполняемому run. Состояние
сообщений, streaming, tools и остановка ответа берутся из runtime. Canvas
получает только типизированные, версионированные и разрешённые представления.
Неизвестный тип безопасно деградирует до объяснимого empty/error state.

Один canonical `workspace-desktop` доступен из sidebar, header, официального
assistant-ui `ComposerPrimitive` и home-кнопки Canvas. Явный вход из Chat
открывает его в exclusive fullscreen; home-кнопка внутри Canvas переключает
текущую вкладку на «Рабочий стол». Все входы используют тот же
`canvas_session_id`, выбранный объект, draft, history, scroll/focus и unsaved
changes. Скрытый второй Canvas или копирование состояния запрещены.

Пока workspace открыт fullscreen, Chat становится официальным assistant-ui
widget с тем же runtime и thread. Он может быть floating или pinned справа на
широком экране и снизу на компактном; изменение положения не создаёт новый
разговор. Закрытие workspace возвращает тот же Chat в центральную поверхность.

Во всех вариантах чата используется официальный assistant-ui
`ComposerPrimitive`, подключённый к тому же runtime и thread. В основном чате,
floating-панели и закреплённом чате composer находится у нижней границы своей
области, а прокручивается только история сообщений. Он сохраняет единые
attachments, send/cancel и streaming-состояния, учитывает safe area и экранную
клавиатуру. Копия textarea с отдельным локальным submit запрещена.

## Единый мультимодальный Canvas

Canvas — одна рабочая сессия для всех сложных представлений:

- базового content mode «Рабочий стол»;
- проектов и их связанных результатов;
- документов, PDF/изображений и document editors;
- смет, таблиц, версий и расчётных редакторов;
- договоров, приложений и сравнения редакций;
- справочников и других структурированных каталогов;
- браузера источников и evidence;
- проверок, findings, diff и разрешённых действий исправления.

Каждое приложение — allowlisted вкладка внутри одной Canvas-сессии. Запуск
проекта, документа, сметы, договора, справочника, браузера, проверки или
редактора меняет только активную вкладку единого Canvas. Приложение не создаёт
окно, вложенный desktop, split-view или отдельный Canvas. Version, provenance,
stale-state и права сопровождают каждую вкладку.

«Рабочий стол» — базовый content mode и спокойный launcher внутри того же
Canvas, когда пользователь ещё не открыл конкретный объект. Он показывает
короткие, приоритетные группы: последние проекты, закреплённые документы,
активные задачи и minimized shelf. Это не отдельная dashboard-поверхность и не
второй Canvas: выбор карточки переключает вкладку текущей `canvas_session_id`, а
возврат открывает тот же launcher с сохранённым контекстом.

Minimized shelf хранит только доступные точки возврата к свёрнутым объектам
этой Canvas-сессии. Это компактный список вкладок, а не MDI, окна или живые
миниатюры приложений. Restore меняет активную вкладку, не создавая ещё один
viewer или параллельный editor. При отсутствии данных «Рабочий стол» остаётся
просторным и тихим: честный empty state, один понятный следующий шаг, без
фиктивных метрик, плотной сетки пустых карточек и декоративного activity feed.

Вкладка «Браузер» использует спокойную трёхчастную композицию:
минимальная непрозрачная chrome-панель, основная page-область и компактная
status-строка. Chrome содержит только разрешённую навигацию и идентичность
источника; page показывает контент/evidence; status сообщает loading, адрес,
дату, trust/error state. Glassmorphism, blur и отдельное браузерное окно не
используются.

Верхний пункт «Документы» и «Документы» внутри выбранного проекта — два входа в
одну и ту же document mode/session. Они передают единый project/document
context и восстанавливают тот же выбранный файл, редактор, draft и позицию.
Повторный вход не открывает копию вкладки, не создаёт новую session и не
раздваивает autosave/history.

## Личный кабинет

«Личный кабинет» — полноценная постоянная поверхность, а не временное меню
аватара. Единственная точка входа в него — профиль в нижнем footer левого
sidebar. В header, Canvas и правой панели дублирующей кнопки профиля нет. В
compact-режиме тот же footer доступен внутри навигационного drawer. Переход
между Chat, Canvas и кабинетом не теряет выбранный проект, thread или
Canvas-сессию.

Кабинет содержит:

- «Профиль»: имя, аватар, подтверждённые контакты, язык, часовой пояс и
  accessibility preferences;
- «Организация и доступ»: активная организация, memberships, роли и доступные
  проекты без возможности повысить собственные полномочия;
- «Безопасность»: поддерживаемые backend способы входа, MFA/SSO, активные
  сессии и отзыв сессии;
- «Уведомления»: каналы и частота продуктовых уведомлений;
- «Тариф и использование»: entitlement, лимиты, usage и документы оплаты;
  покупка или изменение тарифа проходит отдельный подтверждённый gate.

Identity, роли, entitlement и сессии приходят от Product/Data Authority.
Локально сохраняются только безопасные интерфейсные preferences; браузерное
состояние не становится источником полномочий.

Авторизованный superadmin дополнительно видит раздел «AI и провайдеры»:
allowlisted модели MiMo/Codex, назначение маршрутов, health, capability,
лимиты, последнюю проверку и редактированные идентификаторы конфигурации.
Раздел скрыт для остальных ролей, а каждое изменение проходит server-side
policy, audit и отдельное подтверждение для production.

Экран входа честно различает `loading`, `signed out`, `error` и
`unavailable`. Если backend авторизации или разрешённый способ входа не
настроен, интерфейс сообщает «Вход временно недоступен», показывает безопасный
следующий шаг и не создаёт demo-сессию, фиктивный профиль или работающую на вид
кнопку входа.

## Правая контекстная панель

- «Проверка» — выводы проверок, замечания, версии и sign-off; AI approval не
  изображается юридической подписью.
- «Терминал» — структурированный read-only журнал разрешённых команд и
  результатов, а не произвольный браузерный shell.
- «Браузер» — найденные источники, дата доступа и evidence locator.
- «Файлы» — входные и выпущенные артефакты с типом, версией и provenance.
- «Подзадача» — понятный пользователю статус подзадач и зависимостей без
  внутренней служебной переписки и скрытых рассуждений.

Вкладки используют семантику `tablist` / `tab` / `tabpanel`, сохраняют выбранный
режим на время сессии и показывают честный empty state, если данных ещё нет.
«Проверка», «Браузер» и «Файлы» активируют соответствующую вкладку единого Canvas
либо показывают краткую контекстную проекцию; собственный Canvas или дубликат
document/browser session правая панель не создаёт.

## Взаимодействие, motion и доступность

- Все действия доступны с клавиатуры; порядок фокуса следует визуальному
  порядку. Интерактивная цель не меньше `44 × 44 px` на touch-устройствах.
- У кнопок только с иконкой есть русское доступное имя. Активные вкладки,
  ошибки и статусы различимы не только цветом.
- Focus ring всегда видим, текст и controls соответствуют WCAG AA.
- Переходы короткие (`120–200 ms`) и объясняют открытие, закрытие или смену
  состояния. При `prefers-reduced-motion: reduce` необязательная анимация
  отключается.
- Поверхности непрозрачны: backdrop-filter, blur и glassmorphism не используются.
- Streaming-состояние объявляется без чтения каждого токена. Raw reasoning и
  chain-of-thought не выводятся; допускается только безопасный статус работы.

## Граница правдивых данных

Shell может содержать дизайн-демо только при явной метке `Design demo`.
Демонстрационные проекты, суммы, статусы и файлы не должны выглядеть как
полученные с production API.

Факты, допущения, предложения и утверждённые решения показываются раздельно.
Каждая значимая цифра и версия результата должна иметь источник, дату и
provenance. Stale-версия заметно помечается и не получает действие выпуска.
Клиент не придумывает успех, прогресс, доступность инструмента или завершение
подзадачи до server-confirmed event.

Raw credentials MiMo/Codex существуют только внутри Provider Execution
Authority на physical Primary/78. Они не передаются в браузер, Product/Data
Authority, Logical Home Control Plane, prompts, AG-UI events, логи или
артефакты. Личный кабинет показывает только редактированный fingerprint,
версию binding и server-confirmed status; ввод, чтение и копирование raw secret
из UI запрещены. Physical Home не хранит и не авторизует GPT/Codex.

В новом shell/workspace запрещены `dangerouslySetInnerHTML`, `eval` и
произвольный исполняемый HTML/JavaScript. Rich content проходит через
allowlisted renderer и безопасные действия.

## Адаптивность

- `≥1200 px`: трёхколоночный shell с Chat в центре; явный вход заменяет рабочую
  область exclusive fullscreen workspace, а Chat widget floating либо pinned
  справа.
- `768–1199 px`: одна основная рабочая область; навигация и контекст открываются
  поверх неё как drawers; workspace по явному входу остаётся fullscreen.
- `<768 px`: Chat занимает основной viewport, а workspace по явному входу
  становится fullscreen; assistant-ui widget закрепляется снизу. Учитываются
  safe areas, экранная клавиатура и портретная высота `320 px`.
- На всех breakpoints профиль остаётся только в footer левого sidebar/drawer,
  а composer закреплён снизу внутри текущего main/floating/pinned chat и не
  перекрывает сообщения.
- Responsive layout меняет только позицию Chat widget; Canvas остаётся одним
  fullscreen-экземпляром без параллельных desktop/mobile версий.
