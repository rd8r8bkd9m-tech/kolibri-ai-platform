# Архитектура рабочих канвасов Kolibri V3

## Решение

Kolibri — не набор статичных страниц. Оболочка приложения состоит из одной
основной навигации и динамических рабочих канвасов, в которые реестр подставляет
нужную поверхность.

- левый сайдбар — единственная основная навигация;
- основной канвас — постоянный чат, который не размонтируется при работе с
  дополнительными инструментами;
- документ, выбранный из основной навигации, по умолчанию открывается в
  основном канвасе;
- правый канвас создаётся лениво только явным действием «открыть рядом» или
  запуском дополнительного инструмента;
- дополнительный канвас можно изменять по ширине, свернуть, раскрыть и временно
  развернуть на весь экран;
- один канвас может содержать несколько вкладок-поверхностей: файл, редактор,
  браузер, marketplace, проверку или отдельный чат;
- количество дополнительных канвасов в модели не ограничено фиксированным
  числом. Конкретный layout решает, какие из них видны одновременно, а какие
  находятся во вкладках или свёрнуты.

Отдельного статичного `WorkspaceContextSidebar` в целевой архитектуре нет.
Правая область — та же переиспользуемая рамка канваса, а не специальная страница
с собственным набором состояний.

## Слои

### Доменное состояние

`lib/workspace-canvas/` хранит чистую модель и reducer без React и transport:

- `WorkspaceCanvasState` — нормализованный список канвасов;
- `WorkspaceCanvas` — роль, расположение, presentation, контекст и вкладки;
- `CanvasView` — вкладка, содержащая ссылку на поверхность;
- `CanvasSurfaceDescriptor` — тип поверхности и идентификаторы backend-ресурсов;
- `CanvasScope` — связь с проектом, родительским канвасом и будущим
  orchestration channel.

UI-state не копирует документ, проект или беседу. В дескрипторе находятся только
идентификаторы, а единственным источником истины остаётся V3 backend.

### Реестр поверхностей

`createCanvasSurfaceRegistry` объединяет метаданные и renderer payload. Кнопка
не должна импортировать страницу и вручную переключать отдельный boolean. Она
отправляет намерение открыть `CanvasSurfaceDescriptor`; layout получает
определение из реестра и монтирует зарегистрированный renderer.

Добавление marketplace или нового редактора означает одну регистрацию, а не
новую ветку во всех сайдбарах, header и `WorkspaceShell`.

### Рамка

`CanvasFrame` отвечает только за общее поведение:

- вкладки и клавиатурную навигацию;
- свернуть, закрыть, переместить, развернуть;
- accessible tablist/tabpanel;
- единые размеры и chrome.

Рамка не знает, что внутри находится чат, смета или браузер.

### Renderer

Renderer владеет только представлением зарегистрированной поверхности. Он
получает идентификаторы проекта, thread и resource из descriptor, затем читает
данные через действующий browser client соответствующего домена.

## Независимые чаты

Второй чат нельзя реализовать вторым экземпляром старого `AssistantChatWidget`
или ещё одним `Thread` под глобальным `mainThreadId`: такой вариант переключит
основную беседу и смешает состояния.

Для chat surface требуется scoped runtime provider, созданный для конкретного
`threadId` и `canvasId`. Он использует тот же единый product-chat adapter и те же
серверные thread/run endpoints, но имеет отдельный composer, messages и run
state. Основной чат продолжает использовать primary runtime.

Связь канвасов задаётся явно:

- `isolated` — канвас не разделяет проектный контекст;
- `project` — канвасы читают один backend-проект, но имеют независимые thread;
- `orchestrated` — backend-issued channel позволяет агентам обмениваться
  типизированными событиями и ссылками на артефакты.

Frontend не пересылает скрытый текст между чатами и не имитирует оркестратор.

## Переходы состояния

1. `canvas/open` создаёт или активирует независимый канвас.
2. `view/open` добавляет зарегистрированную поверхность как вкладку без
   дублирования стабильного id.
3. `canvas/presentation` переводит auxiliary canvas между `docked`, `expanded`,
   `fullscreen` и `minimized`.
4. Основной канвас нельзя закрыть или свернуть.
5. В один момент времени только один канвас имеет presentation `fullscreen`;
   предыдущий автоматически возвращается в `expanded`.
6. Закрытие auxiliary canvas не меняет main thread и не удаляет backend-ресурс.

## Миграция

1. **Фундамент (выполнен):** чистая модель/reducer, реестр и общий
   `CanvasFrame`; существующий `CanvasWorkspace` использует общую рамку.
2. **Единая композиция:** удалить отдельный desktop context state и
   `WorkspaceContextSidebar`; все открытия проводить через canvas actions.
3. **Навигация:** оставить левый сайдбар authority основной навигации; документы
   и проекты открывать в main canvas, «открыть рядом» — в auxiliary canvas.
4. **Surface renderers:** зарегистрировать files, projects, document, browser,
   marketplace, review и terminal. Недоступные runtime показывают честное
   error/empty state.
5. **Scoped chat:** подключить независимый thread runtime к chat surface без
   восстановления удалённого widget.
6. **Orchestration:** добавить backend-контракт каналов только отдельным ADR и
   миграцией, потому что это новый межпроцессный протокол.
7. **Сохранение layout:** после стабилизации API сохранять только безопасный
   UI-layout; документы и thread остаются ссылками на backend authority.

## Критерии приёмки

- основной чат не исчезает и не меняет thread при открытии файла справа;
- закрытая правая область не занимает место и не запускает renderer/runtime;
- документ можно открыть в основном канвасе и явным действием перенести или
  открыть рядом;
- resize, minimize, restore и fullscreen не теряют выбранную вкладку;
- два chat surface одновременно показывают разные thread и могут отправлять
  сообщения независимо;
- смена проекта в одном auxiliary canvas не переключает основной чат;
- все поверхности имеют loading, empty, error и retry состояния;
- keyboard tab navigation, focus return и Escape работают предсказуемо;
- browser QA подтверждает отсутствие console errors и layout overflow.
