## Детальные карточки

### `kolibri-secondary-control-plane-watchdog`

Русское название: Дежурный второго контура Control Plane.

Назначение: быстро понять, жив ли резервный контур управления фабрикой, отвечает
ли Control Plane и доступен ли Redis.

Частота: каждые 5 минут.

Что проверяет: `http://10.99.0.2:9101/health`, `/v1/nodes`,
`/v1/tasks?summary=1&compact=1`, признак `PONG` от Redis.

Что чинит автоматически: не перезапускает сервисы сам. Обновляет
`ops/secondary-control-plane-watchdog.md`, фиксирует симптом, влияние, последнюю
успешную проверку и безопасные шаги восстановления. Если доступен `gh`, создаёт
или обновляет GitHub issue с метками `P0,factory`.

Когда эскалирует Владиславу: Control Plane недоступен, Redis не отвечает,
несколько проверок подряд не дают свежего heartbeat, требуется restart,
ручной доступ, токены или любое действие сильнее отчёта и issue.

### `kolibri-factory-queue-unblocker`

Русское название: Разблокировщик очереди фабрики.

Назначение: следить, чтобы очередь задач фабрики не застревала и чтобы владелец
видел понятный статус по активным, ожидающим и подозрительным задачам.

Частота: каждые 10 минут.

Что проверяет: summary очереди через Control Plane, первые queued task ids,
leased/running задачи, признаки stale lease и P0-блокеры.

Что чинит автоматически: создаёт или обновляет
`ops/factory-queue-unblocker-report.md`, может повторно подать только уже
проверенный envelope, создать GitHub blocker issue и описать безопасные
следующие действия. Не чистит очередь, не отменяет и не retry'ит чужие задачи
без явного подтверждения.

Когда эскалирует Владиславу: очередь растёт без движения, lease выглядит
протухшим, есть P0-блокер, нужна очистка/отмена/retry чужих задач, сервисный
restart или решение о приоритете задач.

### `kolibri-node-freshness-capacity-monitor`

Русское название: Контролёр свежести и мощности нод.

Назначение: показывать, какие ноды фабрики свежие, какие перегружены, какие
нельзя использовать для новых задач.

Частота: каждые 10 минут.

Что проверяет: `/v1/nodes`, свежесть heartbeat, `draining`, `active_task`,
CPU/RAM/disk, целевую загрузку 80% и резерв 20%.

Что чинит автоматически: обновляет `ops/node-capacity-monitor-report.md`,
создаёт GitHub issue или follow-up при stale node, полном диске или странном
сочетании `draining` с активной задачей. Не заходит по SSH и не меняет системные
настройки.

Когда эскалирует Владиславу: нода stale или заполнен диск, не хватает мощности
под задачи, draining мешает активной работе, нужен доступ к серверу, перенос
нагрузки, расширение ресурсов или ручное вмешательство.

### `kolibri-agent-api-fabric-monitor`

Русское название: Наблюдатель API-связей фабрики.

Назначение: следить, что агенты, субагенты, GitHub и Control Plane действительно
связаны через API-контур, а не через ручные обходные пути.

Частота: каждые 10 минут.

Что проверяет: `/v1/tasks`, `/v1/nodes`, `/v1/agent-messages`, GitHub
issues/PR/Project, наличие fallback/manual gap.

Что чинит автоматически: обновляет `ops/agent-api-fabric-monitor-report.md`,
может отправить read-only probe envelope или agent-message smoke, если это не
мешает очереди. Не выдаёт токены, не меняет permissions, не читает секреты и не
делает destructive actions.

Когда эскалирует Владиславу: API-сообщения не проходят, обнаружен ручной
разрыв процесса, нужны новые permissions, токены, изменение политики доступа или
решение о допустимом repair action.

### `kolibri-subagent-pool-supervisor`

Русское название: Смотритель пула субагентов.

Назначение: держать пул рабочих субагентов Kolibri в целевом размере и не
оставлять завершённые агентские сессии открытыми.

Частота: каждые 15 минут, heartbeat automation.

Что проверяет: список известных активных субагентов, их статусы через
`wait_agent`, целевое правило `6` активных рабочих субагентов.

Что чинит автоматически: для completed-субагентов сохраняет краткий итог,
закрывает их через `close_agent` и создаёт replacement через `spawn_agent` по
очереди ролей из backlog. Не запускает FormulaLM/LLM эксперименты на Mac.

Когда эскалирует Владиславу: активных субагентов меньше целевого числа,
replacement не создаётся, backlog ролей требует приоритизации, агент завершился
с P0-блокером или нужна ручная оценка результата.

### `kolibri-github-project-sync-monitor`

Русское название: Синхронизатор GitHub-проекта.

Назначение: держать GitHub Project, PR, P0 issues и отчёты фабрики в одном
понятном состоянии.

Частота: каждые 15 минут.

Что проверяет: GitHub Project
`https://github.com/users/rd8r8bkd9m-tech/projects/2`, PR `#46`, открытые
P0 issues, labels, CI blocker summaries и ссылки на артефакты.

Что чинит автоматически: синхронизирует только безопасные статусы, ссылки,
пометки `Project sync pending/done` и summaries; обновляет
`ops/github-project-sync-report.md`. Не удаляет Project items, не меняет схему
Project, не закрывает issues/PR без явного основания и не создаёт токены.

Когда эскалирует Владиславу: GitHub Project расходится с реальной работой,
нужно менять структуру проекта, закрывать спорные issues/PR, выдавать новые
scopes или принимать продуктовый приоритет.

### `kolibri-desktop-control-app-mvp-monitor`

Русское название: Наблюдатель MVP desktop-пульта фабрики.

Назначение: следить за прогрессом desktop-приложения, которое должно стать
пультом управления фабрикой через API.

Частота: каждые 20 минут.

Что проверяет: `docs/desktop-control-app.md`,
`ops/envelopes/KOL-DESKTOP-CONTROL-APP-MVP-20260629.json`, PR/CI/Project
статус и Control Plane task status, если envelope уже отправлен.

Что чинит автоматически: обновляет `ops/desktop-control-app-monitor-report.md`,
может безопасно синхронизировать GitHub issue/project status. Не добавляет
desktop dependencies без PR/CI, не запускает GUI-установщики и не создаёт токены.

Когда эскалирует Владиславу: MVP заблокирован, требуется решение о scope,
новые desktop-зависимости, установка через GUI, доступы, токены или изменение
продуктового направления пульта.

### `kolibri-ubuntu-qa-dispatcher`

Русское название: Диспетчер QA на Ubuntu-нодах.

Назначение: отправлять продуктовые проверки на Ubuntu-ноды фабрики, чтобы Mac
не выполнял долгие или неподходящие тесты.

Частота: каждые 30 минут.

Что проверяет: наличие
`ops/envelopes/KOL-PRODUCT-QA-E2E-20260629.json`, состояние QA-задачи в Control
Plane и свежесть QA для текущего head commit.

Что чинит автоматически: если свежей активной или завершённой QA-задачи нет,
отправляет envelope через `ops/kolibri-dispatch --control-url
http://10.99.0.2:9101 submit --file
ops/envelopes/KOL-PRODUCT-QA-E2E-20260629.json`, затем проверяет status/collect и
обновляет `ops/ubuntu-qa-dispatcher-report.md`. Локально делает только
JSON/schema/syntax проверки.

Когда эскалирует Владиславу: QA envelope отсутствует или некорректен, Ubuntu-ноды
недоступны, QA повторно падает, нужен ручной product decision, запуск вне Ubuntu
или расширение тестового контура.

### `kolibri-billing-safety-monitor`

Русское название: Страж безопасного биллинга.

Назначение: не дать изменениям в billing/Т-Банк случайно включить реальные
финансовые операции или небезопасную обработку уведомлений.

Частота: каждый час.

Что проверяет: `backend/billing.py`, `backend/tests/test_billing.py`, безопасные
контрактные проверки, отсутствие реальных финансовых операций, отсутствие
печати секретов, корректность checkout fallback и обязательные поля
notification: `Token`, `TerminalKey`, `Amount`, `PaymentId`.

Что чинит автоматически: запускает безопасные проверки при доступных
зависимостях: `compileall` и `pytest backend/tests/test_billing.py`; обновляет
`ops/billing-safety-monitor-report.md`. Не вызывает реальные T-Банк API без
sandbox и явного подтверждения.

Когда эскалирует Владиславу: есть риск реального списания, нужен sandbox/боевой
доступ Т-Банка, секреты отсутствуют или неверны, тесты billing падают, требуется
решение по тарифам, подпискам или финансовому поведению продукта.

### `kolibri-formulalm-remote-guard`

Русское название: Охранник удалённых запусков FormulaLM.

Назначение: гарантировать, что FormulaLM/Qwen/model benchmark не запускаются на
Mac и проходят только через удалённый Control Plane.

Частота: каждый час.

Что проверяет: git diff/logs на локальные model benchmark commands,
`ollama`/`vllm` execution, claims о локальных артефактах, а также что задачи
FormulaLM идут через
`ops/envelopes/KOL-FORMULALM-REMOTE-BENCH-6H-20260629.json`.

Что чинит автоматически: разрешены JSON validation и Control Plane
status/collect; при риске пишет P0 blocker в
`ops/formulalm-remote-guard-report.md` и GitHub issue. Не запускает модели на
Mac.

Когда эскалирует Владиславу: обнаружен или подозревается локальный запуск модели,
нужна удалённая инфраструктура, remote envelope не проходит, benchmark требует
ручного подтверждения, ресурсов или продуктового решения.

### `kolibri-github-ci-auto-fix-monitor`

Русское название: Авточинитель GitHub CI.

Назначение: следить за GitHub checks и чинить небольшие безопасные поломки CI,
когда причина понятна из логов.

Частота: каждый час.

Что проверяет: текущую ветку, открытые PR через `gh`, статусы GitHub checks и
логи упавших jobs.

Что чинит автоматически: если checks падают по понятной причине, забирает логи,
выделяет root cause, делает минимальный безопасный fix, запускает релевантные
локальные проверки, коммитит и пушит. Если причина внешняя или нужны данные
владельца, обновляет `ops/github-ci-blockers.md` и пишет точный blocker.

Когда эскалирует Владиславу: failure связан с внешним сервисом, секретами,
доступами, спорной продуктовой логикой, крупным рефакторингом, flaky
инфраструктурой или исправление нельзя сделать маленьким безопасным коммитом.

### `kolibri-hourly-verified-github-sync`

Русское название: Почасовой проверенный GitHub-синхронизатор.

Назначение: регулярно сохранять проверенный прогресс из worktree в GitHub и не
пускать непроверенные изменения в историю.

Частота: каждый час.

Что проверяет: `git status`, текущую ветку и изменённые файлы. Для Python
минимум `python3 -m compileall`, для shell `bash -n`, для frontend `npm
build/test`, если изменены frontend-файлы и зависимости доступны.

Что чинит автоматически: если проверки проходят, создаёт ясный commit message с
подходящим префиксом `factory` или `product`, коммитит и пушит текущую ветку в
origin. Если проверки не проходят, не коммитит и обновляет
`ops/hourly-sync-report.md` с точным blocker и следующим действием.

Когда эскалирует Владиславу: проверки падают, git auth/push недоступен, есть
сомнения по секретам или локальным файлам, изменения слишком широкие для
автокоммита, требуется решение о том, что именно считать готовым прогрессом.

## Общие правила эскалации владельцу

Владислава нужно звать, если automation видит P0, требует секреты или новые
доступы, хочет выполнить destructive action, restart, SSH, финансовую операцию,
изменение схемы GitHub Project, закрытие спорного PR/issue, запуск моделей на
Mac или изменение приоритета продуктовых задач.

Базовое безопасное поведение: сначала отчёт, GitHub issue/PR/comment или Control
Plane artifact; затем ручное подтверждение владельца для действий с риском.
