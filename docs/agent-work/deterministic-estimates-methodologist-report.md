# Отчет методолога по детерминированным строительным сметам

Дата проверки: 2026-06-29.
Роль проверки: методолог смет.
Ограничения: FormulaLM/LLM на Mac не запускались; модельные эксперименты не
изменялись; код расчетного движка не изменялся.

## 1. Методологический вывод

Текущий контракт в `docs/agent-work/deterministic-estimates-methodology.md` и
`docs/agent-work/deterministic-estimates-p0-contract.md` сформулирован
корректно для P0: одинаковые канонические входные данные при одинаковых версиях
прайсбука, региона, коэффициентов и правил должны давать одинаковый estimate
JSON.

Важно: точность 98-99% в документах не должна читаться как обещание продукта.
Она допустима только как результат замера на frozen benchmark dataset с
публично указанными версиями данных, датой прогона, commit, numerator и
denominator по каждой метрике. До такого прогона корректный статус:
`not_proven_yet`.

## 2. Что проверено

Проверены документы и код:

- `docs/agent-work/deterministic-estimates-methodology.md`;
- `docs/agent-work/deterministic-estimates-p0-contract.md`;
- `docs/API-RU.md`;

## 3. Подтвержденные сильные стороны контракта

1. В документах уже закреплено главное правило: LLM может помогать с разбором
   текста, но цены, количества, строки, итоги и публикация должны проходить
   через детерминированный расчетный контур.
2. Методология явно требует `input_hash`, версионированный прайсбук,
   региональные правила, audit trail и human QA для коммерчески значимых
   документов.
3. P0-контракт честно отделяет воспроизводимость и арифметическую корректность
   от предметной точности состава работ.
4. В `backend/estimate_engine.py` уже есть демонстрационное детерминированное
   ядро:
   - фиксированный `PRICEBOOK_VERSION = kolibri-ru-2026q2-v1`;
   - фиксированный timestamp для deterministic-смет;
   - canonical text normalization;
   - `input_hash`;
   - deterministic estimate id;
   - пересчет итогов через `Decimal` и `ROUND_HALF_UP`;
   - audit fingerprint для расчета.
5. Тест `test_prompt_estimate_is_stable_for_same_plastering_scope_in_tatarstan`
   подтверждает golden case `100 м2 штукатурки в Татарстане`: два запуска дают
   одинаковый `model_dump(mode="json")`, одинаковый `estimate_id`, регион,
   версию прайсбука и totals.

## 4. Методологические риски и разрывы P0

1. В текущем движке регион хранится как label (`Республика Татарстан`), но для
   строгого контракта нужен стабильный `region_code`, например `RU-TA`.
2. В estimate JSON пока нет полного determinism envelope:
   `rules_version`, `region_profile_version`, `coefficients_version`,
   `engine_version`, `canonicalizer_version`, hash прайсбука и hash правил.
3. Прайсбук находится в коде. Для продукта нужен immutable manifest с hash,
   статусом публикации и valid range. Изменение цены должно создавать новую
   версию или новый manifest hash, не менять старую ревизию.
4. Строкам сметы не хватает методологических полей уровня P0:
   `item_id`, `type`, `pricebook_item_id`, `price_source`, `formula`,
   `quantity_source`.
5. `PriceProvenance.confidence = 0.98` в коде может быть ошибочно прочитан как
   доказанная точность. Методологически это не benchmark metric. Без frozen
   benchmark такое значение должно трактоваться как внутренний атрибут
   источника/уверенности, а не как продуктовый claim.
6. В HTTP API документации пока нет реализованных `/api/estimates/*`
   endpoints. Они описаны в P0-контракте как целевая граница, а не как текущий
   публичный API.
7. Нет подтвержденного benchmark dataset по Татарстану. Значит нельзя писать
   "точность смет 98-99%" без уточнения, что метрика еще не доказана.

## 5. Разрешенные формулировки

Можно использовать:

- "P0 гарантирует воспроизводимость при одинаковом canonical request и
  одинаковых версиях артефактов";
- "арифметика строк и итогов пересчитывается расчетным движком";
- "golden case по штукатурке 100 м2 в Татарстане стабилен в unit test";
- "предметная точность 98-99% является целевой benchmark-метрикой и пока
  требует замороженного эталонного набора";
- "`not_proven_yet`, если benchmark не запускался".

Нельзя использовать до benchmark:

- "система всегда делает сметы с точностью 99%";
- "точность 98%" на основании одного golden case;
- "LLM/FormulaLM гарантирует правильную смету";
- "цены соответствуют рынку" без версии прайсбука, источников и даты проверки.

## 6. Рекомендации к ближайшему P0

1. Зафиксировать `EstimateCanonicalRequestV1` и `EstimateCalculationResponseV1`
   как схемы с обязательным determinism envelope.
2. Вынести прайсбук, региональный профиль `RU-TA`, коэффициенты и правила в
   immutable manifests с hash.
3. Добавить `region_code`, `rules_version`, `pricebook_hash`,
   `region_profile_version`, `coefficients_version` и `canonicalizer_version` в
   расчетный ответ и audit.
4. Переименовать или документально ограничить `confidence = 0.98`, чтобы оно не
   выглядело как заявленная точность сметы.
5. Сделать benchmark endpoint/CLI, который возвращает фактические метрики или
   `not_proven_yet`.
6. Разделить тесты на три класса:
   - determinism tests: должны давать 100% или падать;
   - arithmetic tests: проверяют только расчет;
   - subject accuracy benchmark: единственное место для claims 98-99%.

## 7. Итоговый статус

Методологически текущие документы задают правильную рамку: детерминизм является
контрактом, а точность 98-99% является проверяемой benchmark-целью, не
маркетинговым обещанием. Текущий код подтверждает демонстрационный P0-golden
case, но продуктовый P0 еще требует version envelope, immutable manifests,
строгие поля происхождения цены и benchmark dataset.
