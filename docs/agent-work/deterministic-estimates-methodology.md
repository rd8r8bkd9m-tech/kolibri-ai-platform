# Методология детерминированных строительных смет Kolibri

## 1. Цель

Методология описывает, как Kolibri должен формировать строительные сметы так, чтобы одинаковые вводные всегда давали одинаковый результат. Основной принцип: модель может помогать с разбором текста и предложением структуры, но финальная смета создается детерминированным пайплайном на основе нормализованных вводных, версионированного прайсбука, региональных правил Татарстана, расчетного движка, audit trail и обязательного human QA для коммерчески значимых документов.

Целевой уровень точности 98-99% трактуется как совпадение с утвержденным человеческим эталоном при полном наборе вводных и актуальном прайсбуке:

- 99% арифметической точности по строкам и итогам;
- 98%+ полноты и корректности состава работ/материалов на эталонных кейсах;
- 98%+ корректного выбора позиций прайсбука при наличии однозначного соответствия;
- 100% воспроизводимости результата для одинакового input hash, версии прайсбука и версии правил.

Это не обещание угадать рыночную цену без исходных данных. Если данных недостаточно, система обязана явно вывести допущения и вопросы, а не скрыто достраивать смету.

## 2. Обязательные инварианты

1. Одинаковые нормализованные вводные, версия прайсбука, регион, настройки и версия расчетных правил дают байтово одинаковый estimate JSON.
2. LLM не является источником истины для цен, количеств и итогов. Все итоги пересчитываются в коде.
3. Каждая строка сметы имеет тип: `work`, `material`, `equipment`, `service`, `overhead`, `tax`, `contingency` или `discount`.
4. Каждая цена имеет источник: прайсбук, пользовательская цена, расчетная формула, утвержденное допущение или ручная правка.
5. Любая ручная правка сохраняется как новая ревизия, не перетирая историю.
6. Неизвестные объемы, спорные единицы, дубликаты и выбросы цен блокируют автоподтверждение.
7. Официальные нормативные расценки не создаются искусственно. Они используются только из проверенной базы или пользовательского источника.
8. Коммерческая смета для клиента не выпускается без статуса QA: `approved`, `approved_with_assumptions` или явного `draft`.

## 3. Входные данные

Минимальный вход:

- объект: тип, адрес, регион, площадь, помещения/зоны;
- состав работ: свободное описание или структурированные позиции;
- качество/класс отделки: эконом, стандарт, комфорт, бизнес, индивидуальный;
- ограничения: сроки, бюджет, доступность объекта, работа в жилом доме, ночные/выходные работы;
- материалы: предоставляет заказчик, подрядчик или смешанная схема;
- исключения: что не входит в смету;
- дата расчета и требуемая валидность цен.

Все входные данные проходят канонизацию:

- строки приводятся к единому регистру и нормализованным пробелам;
- адрес и регион приводятся к региональному справочнику;
- единицы измерения мапятся на канонические: `m2`, `m3`, `lm`, `pcs`, `set`, `hour`, `day`, `trip`;
- площади, периметры и количества округляются только по правилам расчетного движка;
- порядок пользовательских списков стабилизируется, если порядок не несет смысла.

На выходе канонизации создается `input_hash`. Он должен входить в audit trail и использоваться в тестах воспроизводимости.

## 4. Архитектура пайплайна

Рекомендуемый поток:

```text
raw_input
  -> canonicalize_input
  -> extract_scope
  -> normalize_estimate_structure
  -> match_pricebook
  -> apply_tatarstan_rules
  -> calculate_quantities
  -> calculate_totals
  -> validate_estimate
  -> human_qa
  -> publish_revision
```

Где:

- `extract_scope` может использовать LLM, но результат должен быть JSON-структурой без финальных расчетов;
- `normalize_estimate_structure` приводит разделы, строки, типы, единицы и названия к справочникам;
- `match_pricebook` выбирает позиции только из активной версии прайсбука;
- `calculate_totals` пересчитывает `line_total = quantity * unit_price` и все агрегаты;
- `validate_estimate` применяет детерминированные проверки;
- `publish_revision` сохраняет неизменяемую ревизию с подписью данных.

## 6. Прайсбук

Прайсбук является главным источником цен. Каждая версия прайсбука неизменяема после публикации.

Обязательные поля позиции:

- `id`;
- `version`;
- `region`;
- `category`;
- `type`;
- `name`;
- `aliases`;
- `unit`;
- `base_unit_price`;
- `min_price`;
- `max_price`;
- `quality_level`;
- `included_operations`;
- `excluded_operations`;
- `material_spec`;
- `labor_norm`;
- `waste_factor`;
- `source`;
- `valid_from`;
- `valid_to`;
- `status`.

Правила работы с прайсбуком:

1. Для расчета используется только опубликованная версия.
2. Обновление цены создает новую версию, а не меняет старую.
3. Если строка не найдена, система создает вопрос или использует явно помеченное допущение.
4. Если найдено несколько близких позиций, система выбирает по ранжированным правилам и сохраняет альтернативы в audit trail.
5. Пользовательская цена допустима, но должна иметь `price_source = user_override`, автора, время и причину.
6. Для Татарстана прайсбук должен хранить локальные коэффициенты и условия применения отдельно от базовых цен.

## 7. Региональная настройка: Татарстан

Для региона `RU-TA` расчет обязан явно применять региональный профиль:

- валюта: RUB;
- регион цен: Республика Татарстан;
- город/зона: Казань, Набережные Челны, Альметьевск, Нижнекамск, прочее;
- логистика: доставка, подъем, удаленность от склада/города;
- сезонность: зимние/летние коэффициенты, если они утверждены в правилах;
- тип объекта: новостройка, вторичное жилье, коммерческое помещение, частный дом;
- условия доступа: лифт, этажность, пропускной режим, ночные ограничения;
- утилизация: вывоз мусора, контейнер, погрузка.

Региональные коэффициенты применяются только если:

- коэффициент есть в опубликованной версии правил;
- входные данные содержат условие применения;
- audit trail фиксирует формулу и источник.

## 8. Расчетные правила

Все расчеты выполняются детерминированно:

- итог строки: `round_money(quantity * unit_price)`;
- итог раздела: сумма строк раздела;
- итог по типу: сумма строк с соответствующим `type`;
- скидка: отдельная отрицательная строка или поле `discount` с явной формулой;
- доставка, overhead, tax и contingency считаются отдельными правилами, а не скрываются в цене работ;
- округление денег выполняется единым методом для всей сметы;
- порядок строк и разделов задается справочником и стабилен.

Запрещено:

- принимать итоговые суммы от LLM без пересчета;
- смешивать работы и материалы в одной строке без явной декомпозиции;
- менять цену старой ревизии при обновлении прайсбука;
- скрывать допущения в комментариях без структурного поля `assumptions`.

## 9. Валидация

Перед QA смета должна пройти проверки:

- все обязательные поля заполнены;
- единицы измерения канонические;
- количество больше нуля, кроме скидок и корректировок;
- цена неотрицательная, кроме скидок;
- `total` каждой строки равен пересчету;
- агрегаты в `totals` равны сумме строк;
- нет дублей по смыслу в одном разделе;
- нет строк с неизвестным источником цены;
- цена не выходит за диапазон `min_price`/`max_price` без объяснения;
- все вопросы и допущения видимы пользователю;
- QA-статус соответствует уровню риска.

## 10. Редактирование

Редактор сметы должен поддерживать:

- добавление, удаление и переименование разделов;
- добавление, удаление и редактирование строк;
- изменение типа строки, единицы, количества, цены, комментария;
- ручную замену позиции прайсбука;
- скидку, доставку, материалы, услуги и резерв;
- автосохранение состояний: `saving`, `saved`, `offline_local_save`, `synced`, `error`;
- сравнение ревизий;
- откат к предыдущей ревизии через создание новой ревизии;
- блокировку публикации, если есть критические ошибки.

Ручная правка не должна ломать детерминизм: повторный расчет той же ревизии с теми же override-данными обязан давать тот же результат.

## 11. Audit trail

Каждая смета хранит журнал:

- кто создал смету;
- исходный `raw_input_hash`;
- `input_hash` после канонизации;
- версия прайсбука;
- версия правил;
- версия модели, если использовалась LLM-экстракция;
- все выбранные позиции прайсбука;
- все коэффициенты и формулы;
- все ручные правки;
- все ошибки валидации;
- результаты QA;
- время публикации ревизии.

Audit trail должен отвечать на вопрос: почему в строке появилась именно эта работа, это количество, эта цена и этот итог.

## 12. Human QA

Human QA обязателен для:

- смет выше заданного денежного порога;
- смет с пользовательскими ценами;
- смет с неизвестными позициями;
- смет с ценовыми выбросами;
- смет с большим числом допущений;
- документов, уходящих клиенту как коммерческое предложение или приложение к договору.

QA-проверяющий подтверждает:

- состав работ соответствует вводным;
- материалы отделены от работ;
- регион и город Татарстана выбраны верно;
- цены взяты из правильной версии прайсбука;
- коэффициенты применены обоснованно;
- арифметика корректна;
- допущения и исключения понятны клиенту;
- смета пригодна для публикации.

Итоговые статусы:

- `draft` - черновик;
- `needs_input` - нужны данные от пользователя;
- `needs_qa` - требуется проверка;
- `approved` - можно выпускать;
- `approved_with_assumptions` - можно выпускать с явными допущениями;
- `rejected` - нельзя выпускать.

## 13. Контроль точности 98-99%

Точность измеряется на эталонном наборе кейсов по Татарстану. Набор должен включать квартиры, частные дома, коммерческие помещения, черновые работы, отделку, электрику, сантехнику, доставку и вывоз мусора.

Метрики:

- `reproducibility_rate`: доля повторов с идентичным JSON;
- `arithmetic_accuracy`: доля строк и итогов без расхождений;
- `scope_recall`: доля эталонных работ, найденных системой;
- `scope_precision`: доля предложенных работ, подтвержденных экспертом;
- `pricebook_match_accuracy`: доля корректных соответствий прайсбуку;
- `qa_escape_rate`: доля критических ошибок, прошедших без блокировки.

Целевые пороги:

- `reproducibility_rate = 100%`;
- `arithmetic_accuracy >= 99.9%`;
- `scope_recall >= 98%` на полных вводных;
- `scope_precision >= 98%` на полных вводных;
- `pricebook_match_accuracy >= 98%` для однозначных позиций;
- `qa_escape_rate = 0` для критических арифметических и price_source ошибок.

## 14. Acceptance tests

1. Reproducibility: два запуска с одинаковыми `raw_input`, `pricebook_version`, `rules_version` и региональным профилем `RU-TA` создают идентичный canonical input, одинаковый `input_hash` и байтово одинаковый estimate JSON.
2. Pricebook immutability: изменение цены в прайсбуке создает новую версию; старая смета при пересчете на старой версии не меняет итог.
3. Arithmetic authority: если LLM вернула неверный `total`, расчетный движок перезаписывает его значением `quantity * unit_price`, а audit trail фиксирует исправление.
4. Татарстан profile: для адреса в Казани смета получает `region = RU-TA`, валюту RUB, городскую зону Казани и применяет только утвержденные региональные коэффициенты.
5. Missing data gate: если площадь помещения или объем работ отсутствуют, смета получает вопрос в `questions` и не может перейти в `approved`.
6. Price source gate: строка без `price_source` или без связи с прайсбуком/ручной правкой блокирует публикацию.
7. Manual override audit: ручное изменение цены создает новую ревизию с автором, временем, старой ценой, новой ценой и причиной.
8. Edit determinism: пересчет отредактированной ревизии с теми же override-данными возвращает тот же JSON и те же totals.
9. Duplicate detection: две смысловые копии одной работы в одном разделе помечаются валидатором и требуют QA-решения.
10. Outlier detection: цена вне диапазона `min_price`/`max_price` требует объяснения или ручного подтверждения.
11. Human QA gate: коммерческое предложение не экспортируется без `qa_status = approved` или `approved_with_assumptions`.
12. Audit completeness: для любой строки можно получить цепочку `raw input -> normalized scope -> pricebook item/user override -> formula -> total -> QA decision`.
13. Accuracy benchmark: на утвержденном эталонном наборе Татарстана система достигает `scope_recall >= 98%`, `scope_precision >= 98%`, `pricebook_match_accuracy >= 98%`, `arithmetic_accuracy >= 99.9%`.
14. Regression stability: обновление модели LLM не меняет финальную смету, если `extract_scope` после нормализации совпадает с прежним canonical scope.
15. Failure fallback: при невалидном ответе LLM система возвращает безопасный черновик с вопросами, не публикует смету и фиксирует причину fallback в audit trail.
