# Backend capability runtime

`GET /api/v1/capabilities` is generated by the canonical runtime registry. It
does not treat a catalog entry, an import or an environment variable as proof
that a capability works.

## Status contract

- `available`: policy, credential source and renderer gates pass, and a fresh
  real invocation probe succeeded.
- `degraded`: the route is configured and permitted, but it has not yet been
  invoked, its evidence is stale, or renderer health is not yet verified.
- `unavailable`: policy/credential/renderer/implementation gates fail, or the
  latest bounded invocation failed without a healthy fallback.

Every capability includes a machine-readable `reason.code`, concrete route
evidence, renderer evidence and the timestamp of a successful proof when one
exists. The probe ledger stores only sanitised verdict metadata; it never
stores prompts, credentials, provider output or artifact bytes.

## Unified tool and artifact contracts

`POST /api/v1/tools/invoke` currently executes these real handlers:

- `web.search`;
- `document.pdf`;
- `document.docx`;
- `document.xlsx`;
- `document.pptx`;
- `image.generate`;
- `image.edit`;
- `site.create`;
- `app.create`.

The file surface is:

- `POST /api/v1/files`;
- `POST /api/v1/files/{id}/analyze`;
- `GET /api/v1/files/search`.

PDF analysis extracts an existing text layer with a bounded `pdftotext`
process. Image-only/scanned PDF returns `pdf_scanned_or_no_text` with
`ocr_supported=false`; the backend does not claim OCR when no OCR route exists.

Generated and uploaded artifacts use one content-addressed store. A successful
result has persisted bytes, MIME, byte size, SHA-256, immutable revision,
download URL, reopen URL and history URL. The backend reopens and verifies the
stored bytes before it reports completion.

The server-persisted verticals `estimate.create` and `document.editor` remain
`degraded` until their corresponding create endpoint completes a real database
write. A successful `POST /api/v1/estimates` or `POST /api/v1/documents`
records only a sanitised result identifier; titles, document content, estimate
rows and raw storage errors are never written to the capability probe ledger.

## Responses extensions

`POST /v1/responses/{id}/retry` creates a new response attempt from a terminal
response context. `Idempotency-Key` is scoped to the source response, so a
replayed retry returns the same new response while a new key creates a new ID.

Responses `text.format.type=json_schema` and Chat Completions
`response_format.type=json_schema` use a bounded strict-schema subset. Request
schemas are rejected before provider invocation when unsupported. Provider
output is buffered, parsed and validated before any successful structured
payload is exposed; invalid output produces an explicit validation failure.

## Deliberately unavailable

The registry currently keeps `integration.connect` and `automation.run`
unavailable. No LLM fallback may turn either into a fake success. They become
available only after a real handler, auth/policy gate and successful invocation
evidence exist.

Image generation keeps its existing real provider route and verified raster
artifact contract. Responses/Chat, cancellation, project history and API keys
keep their existing backend routes; their registry state changes only after a
corresponding real runtime action.
